# SPEC — KBM per-keyboard remap

> ステータス: **方式確定（2026-07-10）／実装は PoC 段階**。

## 0. 決定（2026-07-10、ユーザー回答反映）

- **「キーボード種別」の定義**: レイアウト（JIS/US 等）**と** 物理キーボード個体（Mac / Windows 等）の**両方**を対象。
- **採用方式 = D'（プロファイル切替）**。「キー割当をキーボードごとに変える」の実体は
  **remap 一式（プロファイル）を丸ごと切り替える**こと。切替トリガを二段構えにする:
  1. **手動切替（MVP）**: 設定 UI / トレイ / ホットキーでアクティブプロファイルを選ぶ。**レース無し・確実**。
  2. **自動切替（拡張）**: Raw Input(`WM_INPUT`) でアクティブに打鍵中のキーボードを検出し、
     対応プロファイルへ自動切替。**既知の制約**: 切替直後の最初の1打鍵が旧プロファイルで処理されうる
     （キーボードを持ち替えて打ち始める運用なら実害小）。
- **やらないこと**: 「同一の打鍵ストリーム内で、キーごとにデバイスを見分けて抑制/書換を変える」厳密解。
  これは #1460 の通りフィルタドライバ必須で、PowerToys 本体スコープ外。
- 各プロファイルの remap は**従来どおり LL フックで抑制/書換**する（挙動は現行 KBM と同じ）。
  “per-keyboard” は「どのプロファイルをアクティブにするか」を切り替えることで実現する。

→ 以降の §2 表では **方式 B の“自動切替”部分を D' の拡張として取り込み**、
  Bの弱点（毎打鍵のデバイス精度）は「プロファイル切替トリガの精度」に格下げして許容する。

## 1. 核心の技術的トレードオフ

KBM の remap は `WH_KEYBOARD_LL`（Low-Level Keyboard Hook）で実装されている。
このフックのコールバックは **同期的に「このキーを抑制/書き換えるか」を返す**必要があるが、
イベントに **どの物理デバイス由来かの情報が含まれない**。

一方、物理デバイス識別は **Raw Input（`RegisterRawInputDevices` + `WM_INPUT`）** で可能だが、
Raw Input は**入力を抑制できない**（監視のみ）。しかも `WM_INPUT` はメッセージキュー経由で
LL フックとは**別経路・非同期**に届く。

```
        ┌ 抑制できる ┐        ┌ デバイス識別できる ┐
LL Hook │    ○      │        │        ×         │
Raw Input│   ×      │        │        ○         │
```

→ 「デバイスごとに、元キーを抑制して別キーへ remap」を厳密にやるには、
両方の能力を持つ**フィルタドライバ**（例: [Interception](http://www.oblita.com/interception)）が必要。
これが #1460 が CLOSED（実質保留）になった理由。

## 2. アプローチ候補

| 方式 | デバイス識別 | 抑制 | 実現性 | 備考 |
|---|---|---|---|---|
| A. LL hook のみ（現状） | ✗ | ○ | — | 現行 KBM。デバイス区別不可 |
| B. Raw Input + LL hook 併用（“直近デバイス”ヒューリスティック） | △ | ○ | 中（レースあり） | LL コールバックで「直近に `WM_INPUT` で見えたデバイス」を参照。**同時打鍵・高速切替で誤判定**。単一キーボードで打鍵が交錯しない前提なら実用可能かも |
| C. フィルタドライバ（Interception 等） | ○ | ○ | 低 | 厳密解。だが署名ドライバ配布が必要で Microsoft 受け入れ困難。PowerToys 方針に反する可能性大 |
| D. Raw Input のみ・**抑制なし**（keymap/レイアウト自動切替） | ○ | ✗ | **高** | #12349 相当。打鍵デバイスを検出して「編集対象の keymap セット」や Windows 入力レイアウト/IME を切替。元キー抑制を伴う remap はしない |

## 3. 推奨スコープ（提案）

- **第1段階として方式 D を狙うのが現実的**。
  - `WM_INPUT` で「今アクティブに打鍵しているキーボード」を検出。
  - キーボード → プロファイル（remap セット）の対応表を持ち、アクティブプロファイルを自動切替。
  - “抑制を伴う per-key remap をデバイス単位で”ではなく、“プロファイル（設定一式）をデバイス単位で”切り替える発想。
  - これは #12349（8👍, OPEN）の要望とも一致し、UI も #35632 の「A/B/all ドロップダウン」で素直に表現できる。
- 方式 B は PoC として検証可能だが、レース起因の誤爆リスクを事前に潰す必要あり（要ユーザー合意）。
- 方式 C（ドライバ）は PowerToys 本体としては非現実的。別プロジェクト（ドライバ同梱ツール）として切り出すなら“レポジトリを分ける”判断が初めて意味を持つ。

## 4. 想定コンポーネント（方式 D 前提の暫定）

- Engine 側: Raw Input 受信用の隠しウィンドウ or 既存メッセージループへ `WM_INPUT` 登録。
  デバイスハンドル → デバイス名（`GetRawInputDeviceInfo` / `HidD_GetProductString`）解決。
- 設定: `default.json` にプロファイル概念を追加、またはプロファイルごとに別ファイル。
  デバイス識別子（HID の VID/PID + シリアル等）とプロファイルの対応表。
- Editor(WinUI3/C#): 編集対象プロファイルを選ぶドロップダウン、検出済みキーボード一覧表示。

> 上記は方式が D に確定してから詳細化する。現時点では“候補”に過ぎない。

## 6. 実装オリエンテーション（PoC 調査反映・2026-07-10）

> 詳細な file:line と実機データは [poc/POC-RESULTS.md](poc/POC-RESULTS.md)。

- **朗報: プロファイル切替の土台は既存**。KBM は `settings.json` の `activeConfiguration` に応じて `{name}.json` を読み、保存時イベントで**エンジンがホットリロード**する（`common/MappingConfiguration.cpp:410/450/652`）。実際は `"default"` のみ・切替 UI 無し。
  → **MVP（手動切替）= 既存 named-config 機構を流用**。`activeConfiguration` を書き換えて reload イベントを叩くだけ。新規の設定永続化は不要。
- **自動切替はエンジンにウィンドウ新設が必要**。エンジンはフックのみでウィンドウ無し（`KeyboardManagerEngine/main.cpp:17`, `run_message_loop`）。`WM_INPUT` は WndProc 必須なので **message-only window + `RegisterRawInputDevices(RIDEV_INPUTSINK)`** を追加する。
  → 雛形: FancyZones `fancyzones/FancyZonesLib/KeyboardInput.cpp`（`RegisterRawInputDevices`/`GetRawInputData`）。
- **ドライバ不要**を再確認（抑制は従来 LL フックのまま。per-keyboard はアクティブプロファイル切替で表現）。
- Editor 側の足場: `EditorSettings.cs` に未配線の `ProfileDictionary`/`ActiveProfile` あり。UI 追加先は `Pages/MainPage.xaml(.cs)`、橋渡し `Interop/KeyboardMappingService.cs`。

## 7. 2台以上を同時接続したときの設計（PoC 実測反映・2026-07-11）

> 前提の再確認: アクティブなプロファイルは**常に1つ**で、LL フックが**全打鍵に**適用する。
> 2台つないでいても「同時に別々の remap」は原理的に不可（ドライバ方式=スコープ外）。
> 制御できるのは「今アクティブなプロファイルを、どのキーボードに合わせるか」だけ。
> 実測データ・根拠は [poc/POC-RESULTS.md](poc/POC-RESULTS.md) §4。

### 識別キー（確定）
- **主キー = `RIDI_DEVICENAME` のデバイスパス文字列**。常に存在・一意・安定。
  VID/PID が取れない実機の2台目（`\\?\HID#Target_KIP&...`）も安定して区別できた。
- VID/PID・HID 製品名は**表示用の親切ラベル**（USB/BT で判別しやすいが、無いこともある）。

### 切替ポリシー（既定）
1. **手動切替を MVP の主役に**（ホットキー / トレイ / 設定）。レース皆無・確実。
2. **自動切替は拡張**: 「最後に打鍵したキーボードが勝つ」＋**ヒステリシス**（新デバイスで
   連続 N 打鍵 or T ミリ秒継続で初めて切替）。素の1打鍵即切替は交互打鍵で thrashing するため禁止。
3. **打鍵/修飾キー保持中は切替を保留**（全キー解放まで）。コンボ中のプロファイル変化を防ぐ。

### 必須ルール（PoC で判明した落とし穴）
- **R1: `hDevice == NULL`（注入/合成入力）では絶対に切り替えない。** KBM 自身の remap 出力も
  NULL で戻るため、切り替えると自己出力が切替を誘発して破綻する。NULL は「現プロファイル維持」。
- **R2: 「検出キーボード一覧」は列挙(`GetRawInputDeviceList`)＋実打鍵の両方から学習。**
  実測で列挙結果(Logitech 046D)と打鍵時デバイス(`Target_KIP`)が食い違った。
- **R3: 集約プロバイダの制約を明記。** 複数キーボードが1つのプロバイダパス配下に集約される
  環境では個別区別できない。その場合は手動切替にフォールバック。
- **R4: 未割当デバイス → 既定プロファイル（または remap なし）。切断時 → 既定 or 残デバイスのプロファイル。**
- **R5: 可視化**（トレイ/トースト）で現アクティブプロファイルを表示＋**手動固定オーバーライド**を用意。

### 一言まとめ
> 「パスで識別／最後に打鍵したキーボードが勝つ＋ヒステリシス／NULL 注入と修飾キーは数えない／
> いつでも手動・ホットキーで切替できる」。真の同時個別 remap は非対応と明記。

### 既定ポリシー（確定 2026-07-11）
- **既定 = 手動切替。自動切替は設定で任意 ON。** MVP は手動のみで出し、自動は拡張として後付け。

### 自動切替の確定仕様と制約（実機実証済み 2026-07-12）
- 判定対象は「注入でない・キーダウン・**非修飾キー**」のみ。ヒステリシス = 連続2打鍵（`AutoSwitchThreshold=2`）。
  （修飾キー除外の理由: チョード（巡回ホットキー含む）の先頭に必ず来てカウントを汚染するため。実測で確認）
- **制約1（Windows パイプライン）**: アクティブプロファイルで remap されたキーは LL フックが抑制するため
  Raw Input に届かず、**切替の判定材料にならない**。remap 対象キーだけの連打では切替は発火しない。
  通常のタイピング（非 remap キーを含む）では2打で発火する（実証: `qwe8`）。
- 制約2: 切替直後の最初の1〜2打は旧プロファイルで処理される（非同期リロードの本質的レース）。
- 制約3: 長押し（オートリピート）は Raw Input 上1打鍵扱い。
- **ホットキー巡回切替（実装・実証済み）**: `deviceProfiles.json` の `cycleHotkey`（{win,ctrl,alt,shift,code}）で
  グローバルホットキーを登録。押すたび keyboardConfigurations を巡回＋ビープ。未定義なら無効（既定）。
  確実・即時の手動切替手段として自動切替の制約を補完する。
